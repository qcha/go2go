# Сбор результатов из горутин через канал

## Условие

Функция запускает обработку задач в отдельных горутинах, собирает результаты в канал и в итоге возвращает слайс.

Тип `Task` и функция `process` опущены. Считаем, что `process(t)` возвращает `Result`.

```go
import "sync"

type Result struct {
    ID  int
    URL string
}

func Resize(tasks []Task) []Result {
    results := make(chan Result)
    var wg sync.WaitGroup
    for _, t := range tasks {
        wg.Add(1)
        go func(t Task) {
            defer wg.Done()
            results <- process(t)
        }(t)
    }
    wg.Wait()

    var out []Result
    for r := range results {
        out = append(out, r)
    }

    return out
}
```

Вопросы:

* Что произойдет при выполнении этого кода?
* Почему возникает проблема?
* Как можно исправить код?
* Какие варианты исправления есть и чем они отличаются?

## Решение

В коде есть две проблемы.

Первая: `results` - небуферизованный канал. Отправка в такой канал блокируется до тех пор, пока другая горутина не начнет читать из него.

В этом коде чтение из `results` начинается только после `wg.Wait()`. Но `wg.Wait()` ждет завершения всех горутин, а каждая горутина не может завершиться, потому что зависает на отправке результата в канал. Поэтому возникает `deadlock`.

Вторая проблема: канал `results` никто не закрывает. Цикл `for r := range results` завершится только после закрытия канала, поэтому без `close(results)` у него нет корректного выхода.

Корректное решение должно сделать две вещи:

* начать читать из `results` до того, как все горутины завершатся;
* закрыть `results` после того, как все отправители закончат работу.

### Вариант 1: читать в основной горутине, закрывать канал в отдельной

В этом варианте основная горутина сразу переходит к чтению из `results`, поэтому рабочие горутины не блокируются навсегда на отправке. Отдельная горутина ждет завершения всех обработчиков через `wg.Wait()` и после этого закрывает канал, чтобы цикл `range results` мог завершиться.

```go
func Resize(tasks []Task) []Result {
    results := make(chan Result)

    var wg sync.WaitGroup
    for _, t := range tasks {
        wg.Add(1)
        go func(t Task) {
            defer wg.Done()
            results <- process(t)
        }(t)
    }

    go func() {
        wg.Wait()
        close(results)
    }()

    out := make([]Result, 0, len(tasks))
    for r := range results {
        out = append(out, r)
    }

    return out
}
```

### Вариант 2: использовать буферизованный канал

Если размер буфера равен количеству задач, каждая горутина сможет отправить результат в канал еще до начала чтения. После `wg.Wait()` все отправители уже завершились, поэтому канал можно закрыть и прочитать накопленные результаты.

```go
func Resize(tasks []Task) []Result {
    results := make(chan Result, len(tasks))

    var wg sync.WaitGroup
    for _, t := range tasks {
        wg.Add(1)
        go func(t Task) {
            defer wg.Done()
            results <- process(t)
        }(t)
    }

    wg.Wait()
    close(results)

    out := make([]Result, 0, len(tasks))
    for r := range results {
        out = append(out, r)
    }

    return out
}
```

## Итого

Предпочтительный вариант - первый: начать читать из канала сразу, а закрытие канала вынести в отдельную горутину после `wg.Wait()`.

Буферизованный канал тоже решает эту конкретную задачу, если размер буфера равен количеству задач. Но это менее универсальное решение: оно зависит от размера буфера и хуже подходит для большого числа задач. Если буфер сделать меньше количества задач, `deadlock` может вернуться.
